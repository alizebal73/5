# ماتریس مرجع نیازمندی‌ها و رهگیری — GameNet 5

این سند، فهرست مرجع نیازمندی‌های محصول و معیارهای پذیرش آن است. هر قابلیت قبل از کدنویسی باید مالک، دادهٔ مرجع، وابستگی، مجوز، رفتار در خطا/رقابت، آزمون و شواهد پایان کار مشخص داشته باشد. وجود صفحه، endpoint، entity یا تست واحد به‌تنهایی وضعیت «تکمیل‌شده» ایجاد نمی‌کند.


## استاندارد اجرایی UI و تکمیل عمودی قابلیت‌ها

قواعد لازم‌الاجرا برای جداسازی View/XAML از ViewModel/Command، استفادهٔ مجدد از عملیات واقعی، قرارداد Action Catalog، ساخت UI همراه هر قابلیت، تست‌های Binding/Resource/Command و معیار تحویل هر برش در [قرارداد توسعهٔ UI و پیاده‌سازی عمودی قابلیت‌ها](../development/ui-architecture-and-vertical-slice-policy.md) ثبت شده است. این سند مکمل ماتریس نیازمندی‌هاست و مالکیت دامنه/قواعد تجاری جدیدی ایجاد نمی‌کند.

قبل از شروع هر قابلیت، این سیاست همراه با [Definition of Ready](definition-of-ready.md) بررسی شود؛ موقع بستن آن، [Definition of Done](definition-of-done.md)، Requirement ID و شواهد exact-SHA معیار هستند. ناهماهنگی وضعیت بعضی برچسب‌های فاز در اسناد راهبردی جداگانه در [Issue #77](https://github.com/alizebal73/5/issues/77) پیگیری می‌شود؛ این کار مرحلهٔ بسته را خودبه‌خود باز نمی‌کند.

## Canonical module ownership — Stage 2 decision

| Module | Canonical ownership | Boundary / dependency rule |
|---|---|---|
| Identity | Operator accounts, roles, permissions and operator authentication | No separate Users module; Customer identity is separate |
| Stations | Station ID/code/type and administrative status | Not Agent connection or Session occupancy |
| Agents | Device enrollment/credentials, heartbeat, lease/fencing and device-state reconciliation | Does not decide operator command permissions or billing |
| ClientControl | Server-authorized PC command policy, lifecycle and result | Dispatches through Agents; must fail closed |
| Customers | Customer profile/code/PIN and activation state | Does not own wallet/debt/session/station state |
| Sessions | Session lifecycle, ownership, authoritative timing and recovery state | Consumes Station/Customer/Agent facts; doesn't own pricing or wallet |
| Tariffs | Rate plans, applicability and immutable price snapshot | No invoice/payment or wallet balance ownership |
| Billing | Bill preview/checkout, invoices, actual payment records/allocation, pending settlement, refund/reversal workflow | Coordinates Wallet/Inventory through an idempotent transactional boundary where required |
| Wallet | Purchased balance, free money/time, debt and associated immutable ledgers/projections | Pending invoice is not Debt; actual cash receipt isn't a wallet transfer |
| Inventory | Locations and stock ledger, receiving, moves, counts, waste, return/correction | Buffet owns order lifecycle |
| Buffet | Order/sale state and coordination with Billing/Inventory | Does not directly set stock or wallet totals |
| VIP | Plans, entitlement and usage limits/ledger | Uses Tariffs/Sessions; does not duplicate price calculation |
| Games | Catalog and Server-authorized launch policy | Agent is executor, not authority |
| GameAccounts | Shared game-account pool and account lease/release/recovery | Blocked until ADR-0003 and secret lifecycle are accepted |
| Shifts | Cash opening, reconciliation, shift close/handover | Separate from read-only Reports |
| Reports | Read-only projections for revenue, sessions, wallet, stock, shifts and audit | Never a source of truth |
| Settings | Validated/versioned Server-backed policies and configuration | Domain owners still validate their own rules |
| Approvals | Extra approval requests/decisions for specified high-risk mutations | Owning module performs the actual approved mutation |
| Backup | Backup/verification/restore orchestration and evidence | Domain modules own their own reconciliation |

Capability decisions: Discounts/promotions are Billing/Tariffs capabilities for version one; Network policy is configured under Settings and executed through ClientControl/Agents only where supported; diagnostics/observability/time/money/transactions/audit/idempotency/outbox/persistence remain cross-cutting platform services. Tests live in root `tests/` projects under module-specific paths.

## ۱۱) Definition of Ready / Done

**قبل از شروع کار (Ready):** شناسهٔ REQ، کاربر/actor، نتیجهٔ تجاری، owner، منبع دادهٔ authoritative، dependencies، permission، state transition، transaction/idempotency/concurrency، رفتار failure/recovery، API/Desktop/Agent contract، risk و معیارهای قابل‌آزمون مشخص باشند. سؤال باز مؤثر روی پول، امنیت، مالکیت یا release نباید ضمن کدنویسی به تصمیم پنهان تبدیل شود.

**برای Done:** پیاده‌سازی واقعی Server/persistence، Desktop/Agent path در صورت نیاز، permission، audit، idempotency، concurrency، error mapping فارسی، migrations، tests (unit/integration/contract/E2E متناسب)، observability، update/recovery اثرپذیر و evidence روی SHA دقیق بررسی شود. برای release، تست Windows/PostgreSQL/Agent و physical gate موردنیاز است. هر الزام ناتمام باید status و مدرک صریح داشته باشد؛ «ظاهر صفحه آماده است» معیار نیست.

## ۱۲) جمع‌بندی تصمیم‌های قطعی مرحلهٔ ۴

1. معماری محصول Repo 5 حفظ می‌شود: modular monolith Server + Native WPF Desktop + Windows Agent جدا + Shared contracts + PostgreSQL. پیشنهاد تاریخی React/SQLite در Repo 2 برای این محصول مرجع فنی نیست.
2. PC دارای Agent است؛ PS5 و فوتبال‌دستی دستگاه‌های زمان‌دار هستند و Agent ساختگی دریافت نمی‌کنند.
3. ledgerهای Wallet و Inventory، AccountStateهای Pending/Debt، Session ownership، Agent lease/fencing و Audit مرزهای غیرقابل‌چشم‌پوشی‌اند.
4. قابلیت‌های کمکی مثل Reservation، Tournament، SMS، mobile app، multi-shop، CCBOOT/PXE و payroll کامل به‌عنوان توسعهٔ بعدی باقی می‌مانند، نه mock یا دکمهٔ نیمه‌فعال در هسته.
5. وضعیت فعلی Repo 5 پس از Identity و Stations هنوز محصول کامل یا release-certified نیست؛ ماژول/آزمون جدید تا عبور گیت مربوط به همان SHA «نامزد پیاده‌سازی» می‌ماند.
6. هیچ کدی از Repo 2 یا Repo 3 در این مرحله merge نشد. این مرحله فقط نیازمندی و معیار پذیرش را تثبیت می‌کند.
