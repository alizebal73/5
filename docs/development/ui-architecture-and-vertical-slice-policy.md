# قرارداد توسعهٔ UI و پیاده‌سازی عمودی قابلیت‌ها — GameNet 5

**وضعیت:** استاندارد اجرایی پیشنهادی برای استفاده در تمام برش‌های محصول؛ تکمیل یک صفحه یا یک ماژول به‌تنهایی معیار Done نیست.  
**ارتباط با نقشهٔ راه:** این سند مکمل `docs/planning/master-build-plan.md`، ماتریس `docs/planning/requirements-traceability.md` و معیارهای `definition-of-ready.md` / `definition-of-done.md` است.  
**پیگیری هم‌ترازی وضعیت اسناد:** [Issue #77](https://github.com/alizebal73/5/issues/77).

## 1. قواعد پایه

1. **یک قابلیت را به‌صورت عمودی و قابل استفاده تحویل بده.** برای هر برش، نیازمندی، UI، قرارداد Shared، API و منطق Server، persistence/migration لازم، مجوز، Audit، آزمون و شواهد CI را با هم کامل کن. از ساخت تعداد زیادی صفحه یا entity بی‌اتصال به‌عنوان «پیشرفت محصول» خودداری کن.
2. **Server مرجع قواعد و وضعیت تجاری است.** Desktop و Agent فقط از قراردادهای مجاز درخواست/مشاهده می‌کنند؛ هیچ قانون authoritative برای قیمت، زمان قابل‌محاسبه، مالکیت Session، ماندهٔ کیف پول، بدهی یا موجودی در UI/Agent قرار نمی‌گیرد.
3. **هر قانون یک مالک دارد.** قابلیت را در ماژول مالک پیاده‌سازی کن و از API/قرارداد صریح برای ارتباط ماژول‌ها استفاده کن. برای رفع یک نیاز، منطق مشابه را در چند ماژول یا صفحه تکثیر نکن.
4. **پایان کار با شواهد سنجیده می‌شود.** وجود کد، endpoint، جدول، صفحه، mock یا تست واحد به‌تنهایی نشان‌دهندهٔ تکمیل نیست. نتیجه باید با Requirement ID و معیار پذیرش آن قابل ردیابی باشد.
5. **هر برش باید شکست و بازیابی را مشخص کند.** پاسخ تکراری، timeout، قطعی شبکه، لغو درخواست، دسترسی غیرمجاز، هم‌زمانی و راه برگشت/اصلاح عملیات مرتبط را پیش از اعلام Done بررسی کن.
6. **یک مرحلهٔ اصلی در هر زمان.** کارهای موازی فقط وقتی مجازند که وابستگی‌ها، فایل‌های مشترک و دروازه‌های پذیرش با هم تداخل نداشته باشند.

## 2. قرارداد اتصال UI به عملیات

### View / XAML — ظاهر

- XAML مسئول چیدمان، تب‌ها، جدول‌ها، کارت‌ها، رنگ و استایل، Binding و نمایش وضعیت است؛ محاسبهٔ مالی، قانون تجاری، مجوز یا دسترسی مستقیم به PostgreSQL در آن ممنوع است.
- پوستهٔ اصلی، Navigation و صفحه‌های قابلیت باید به‌تدریج جدا شوند. تغییر رنگ، محل دکمه، تب، کارت یا جدول نباید مستلزم تغییر قانون تجاری باشد.
- استایل‌ها، رنگ‌ها، فونت‌ها، اندازه‌ها و الگوهای تکراری UI را تا حد امکان در Resources/Design Tokens مشترک قرار بده؛ برای مدرن‌کردن ظاهر، استایل ده‌ها صفحه را دستی و جداگانه تکثیر نکن.
- صفحات/حالت‌های UI را از نیاز واقعی بساز؛ تب یا دکمهٔ نمایشی بدون عملیات پیاده‌شده، مسیر موفقیت جعلی یا mock ماندگار در برنامهٔ عملیاتی ایجاد نکن.

### ViewModel / Command — آداپتور تعامل کاربر

- ViewModel وضعیت قابل‌نمایش صفحه، انتخاب کاربر، اجرای در حال انجام، خطا و Commandها را مدیریت می‌کند.
- هر Command باید ورودی مشخص، وضعیت اجرا و امکان/عدم امکان اجرا داشته باشد. وضعیت `CanExecute` برای تجربهٔ کاربر مفید است، ولی **کنترل امنیتی نیست**؛ Server باید مجوز را مستقلاً بررسی کند.
- عملیات تجاری تکراری را در code-behind یا ViewModelهای مختلف دوباره پیاده‌سازی نکن. چند صفحه می‌توانند آداپتور/Commandهای UI جدا داشته باشند، اما باید به یک عملیات/use case معتبر و قرارداد Server یکسان متصل شوند؛ لازم نیست یک نمونهٔ واحد از `ICommand` را به‌زور در همهٔ صفحه‌ها مشترک کنی.
- code-behind فقط برای رفتارهای خاص کنترل/چارچوب WPF که Binding عادی آن‌ها را پوشش نمی‌دهد مجاز است؛ برای نمونه مدیریت محدود رویدادهای `PasswordBox`، focus یا پاک‌کردن امن کنترل. قانون تجاری، محاسبات و فراخوانی‌های پراکندهٔ API را در آن قرار نده.
- در حالت Busy از اجرای دوبارهٔ ناخواسته جلوگیری کن؛ خطای Server را به پیام قابل‌فهم تبدیل کن، بدون اینکه پاسخ موفقیت را پیش از تأیید Server نمایش بدهی.

### API client / Shared contract — مرز اتصال

- قراردادهای typed در `src/Shared/Contracts` مرجع درخواست/پاسخ‌اند؛ از DTO موازی و parsing متن exception برای تشخیص خطا استفاده نکن.
- Desktop از طریق رابط‌های API client با Server حرف می‌زند. Desktop و Agent اتصال مستقیم به PostgreSQL ندارند.
- هر mutation باید قرارداد روشن برای ورودی، خروجی، خطاهای پایدار، Permission، correlation و idempotency داشته باشد. برای عملیات پولی/حساس، رفتار تکرار درخواست، timeout نامشخص و پاسخ گم‌شده صریحاً تعریف شود.
- تغییر ناسازگار قرارداد را با versioning/ADR و آزمون قرارداد مدیریت کن؛ تغییر UI نباید بی‌خبر قرارداد Server را بشکند.

### Server — اجرای معتبر

- Server اعتبارسنجی ورودی، مجوز مؤثر، قانون دامنه، تعرفه/زمان، تراکنش، idempotency، کنترل هم‌زمانی، Audit و نتیجهٔ نهایی را اجرا می‌کند.
- عملیات حساس باید actor، هدف، زمان، correlation و علت موردنیاز را ثبت کند. دلیل ارسالی UI ورودی غیرقابل‌اعتماد است و باید روی Server اعتبارسنجی شود.
- نتیجهٔ UI فقط پس از پاسخ معتبر Server و با توجه به وضعیت persisted/reconciled اعلام شود. پس از timeout، نتیجه را حدس نزن؛ وضعیت را دوباره از Server بخوان یا با idempotency key معتبر همان عملیات را پیگیری کن.

## 3. Action Catalog — فهرست یگانهٔ عملیات قابل‌فراخوانی

برای هر عملیات کاربرمحور/حساس، پیش از پیاده‌سازی یا گسترش UI مشخص کن:

| فیلد | چیزی که باید ثبت شود |
|---|---|
| شناسه و نام عملیات | نام پایدار و یکتا، مانند `sessions.extend`؛ نام نمونه به معنی وجود پیاده‌سازی نیست |
| مالک | ماژول و use case مالک عملیات |
| نتیجهٔ کاربر | چه چیزی واقعاً تغییر می‌کند و چه چیزی صرفاً خوانده/نمایش داده می‌شود |
| قرارداد | Request/Response در Shared، خطاهای قابل‌شناسایی و نسخه |
| مجوز | Permission سمت Server؛ در صورت نیاز علت/تأیید اضافی |
| ورودی و پیش‌شرط | موجودیت انتخاب‌شده، وضعیت لازم، محدودیت‌ها و اعتبارسنجی |
| تکرار/رقابت | Idempotency، قفل/قید یا کنترل هم‌زمانی لازم |
| آثار جانبی و Audit | تغییرات مالی/موجودی/نشست، رویدادهای Audit/Outbox و امکان لغو/معکوس‌سازی |
| سطوح UI | تب/صفحه/داشبورد/منوی زمینه‌ای که عملیات در آن ظاهر می‌شود و تفاوت پارامترهای هر محل |
| حالت‌های UI | loading، disabled، empty، offline، timeout، denied، conflict و موفقیت تأییدشده |
| شواهد | آزمون‌های ViewModel/API/Server/PostgreSQL و Requirement ID مرتبط |

Catalog قرار نیست مالک دوم قانون تجاری شود؛ سندی برای شفاف‌کردن اتصال UI به عملیات رسمی است. اگر یک عملیات در چند محل ظاهر می‌شود، تمام محل‌ها باید همین تعریف و قرارداد را مصرف کنند. اگر دو عمل اثر مالی/دامنه‌ای متفاوت دارند، آن‌ها را صرفاً به دلیل شباهت ظاهر با هم یکی نکن.

## 4. استاندارد تجربهٔ کاربری GameNet

- فارسی و `fa-IR` حالت اصلی و راست‌به‌چپ باشد؛ `en-US` چپ‌به‌راست از Resources/فرهنگ مناسب استفاده کند. رشته‌ها را در XAML پراکنده و سخت‌کدشده تکثیر نکن.
- ارائهٔ تومان، تاریخ/زمان، اعداد و قالب‌بندی locale را از محاسبات authoritative جدا نگه دار. قالب نمایشی نباید منبع محاسبهٔ پول یا زمان باشد.
- فهرست ایستگاه‌ها باید برای تعداد قابل‌افزایش رایانه‌ها مقیاس‌پذیر، قابل جست‌وجو و فیلتر بر اساس نوع/وضعیت باشد؛ PC، PS5 و فوتبال‌دستی نباید مدل Agent یکسان و ساختگی داشته باشند.
- در کارت/ردیف ایستگاه قیمت ساعتیِ authoritative نمایش نده؛ تعرفهٔ قابل‌اعمال باید طبق قرارداد Server و زمینهٔ عملیات مشخص شود.
- برای عملیات پرتکرار اپراتور، ناوبری روشن، مسیر کوتاه، جست‌وجو/فیلتر و در صورت نیاز منوی زمینه‌ای فراهم کن؛ ناوبری تکراری/دوگانه نساز مگر نیاز مشخصی آن را توجیه کند.
- برای هر صفحهٔ عملیاتی، وضعیت‌های loading، empty/no-results، error، offline/reconnecting، denied، conflict و نتیجهٔ موفق تأییدشده را طراحی کن.
- کیبورد، focus، انتخاب فعلی، پیام خطا، اندازهٔ پنجره و پاک‌کردن PasswordBoxها را در طراحی در نظر بگیر. تغییر ظاهر نباید رفتار دسترسی‌پذیری یا امنیت ورود را خراب کند.

## 5. تست‌ها و شواهد هر برش

آزمون‌های لازم را با توجه به اثر برش انتخاب کن؛ همهٔ دسته‌های زیر برای هر تغییر کوچک لازم نیستند، اما هیچ آزمون مرتبطی نباید به خاطر سبز بودن آزمون نامرتبط حذف شود.

- **View/Binding/Resources:** آزمون binding، resource key، ترجمه و وضعیت دسترسی/فعال‌شدن Command.
- **ViewModel/Command:** آزمون ورودی نامعتبر، Busy، موفقیت تأییدشده، خطای typed، timeout، عدم مجوز و عدم ارسال درخواست ناخواسته.
- **API/Contract:** درخواست/پاسخ typed، نسخه، کد خطای پایدار، correlation و idempotency.
- **Server/Domain:** قواعد مالک دامنه، permission، audit، تراکنش و پاسخ خطا.
- **PostgreSQL:** migration، rollback، قید/رقابت، idempotency و invariants برای تغییرات پایدار/حساس.
- **End-to-end:** مسیر کاربر از UI تا وضعیت معتبر ذخیره‌شده و برگشت نتیجه به UI؛ برای اولین چرخهٔ کسب‌وکار، نتیجهٔ پول/نشست/مالکیت را از دادهٔ مرجع اثبات کن.
- **Invariantهای حیاتی:** برای ماشین حالت Session، دفترکل پول/موجودی و قواعد رقابتی، آزمون‌های پارامتری گسترده یا property-based در جایی که ارزش دارد به‌کار ببر؛ دست‌کم invariants مالی و مالکیت باید صریح و آزمون‌پذیر باشند.
- **CI و ثبت شواهد:** نتیجهٔ لازم روی همان SHA کاندید ثبت شود؛ green قدیمی برای کد جدید قابل‌قبول نیست. PR تا وقتی بررسی/تصمیم لازم ثبت نشده، خودکار merge نشود.
- **بازبینی تعاملی:** UI هم‌زمان با هر برش ساخته می‌شود و نباید تا پایان پروژه موکول شود. sanity check توسعه‌ای را هر جا امکان امن دارد انجام بده؛ پذیرش نهایی کامل RTL/LTR، keyboard/focus، سرویس نصب‌شده، نصب/ارتقا و LAN طبق نقشهٔ راه روی کاندید انتشار و محیط آزمایشی جدا انجام می‌شود.

## 6. قطع ارتباط، ساعت و مقاومت در برابر دستکاری

- سیاست قطع Server/Agent باید پیش از تکمیل Sessions مشخص باشد: زمان authoritative، وضعیت Session حین قطع، مهلت مجاز در صورت وجود، رفتار هنگام اتصال مجدد، reconcile کردن زمان/هزینه و نتیجهٔ مبهم درخواست.
- از ساعت Client/Agent به‌عنوان مرجع پول یا مدت قابل‌صورتحساب استفاده نکن؛ سیاست زمان را Server تعریف و ذخیره می‌کند.
- مدل تهدید Agent را مستند کن: بسته‌شدن/خرابی process یا service، restart، تغییر ساعت، قطع شبکه، لغو credential، دستکاری فایل/config و تلاش برای replay. تشخیص، fail-closed، بازیابی و ثبت Audit را آزمون کن.
- ادعای غیرواقعی «جلوگیری کامل نرم‌افزار از Task Manager، Safe Mode یا همهٔ روش‌های دستکاری سیستم‌عامل» نکن؛ حدود کنترل ویندوز/حساب کاربر/سرویس/ACL را مشخص کن و هر سخت‌سازی وابسته به سیاست سیستم‌عامل را جداگانه اعتبارسنجی کن.
- آزمایش Service identity، effective ACL، DPAPI، دسترسی TLS private key پس از restart، enrollment و LAN را از unit/loopback/ZIP نتیجه‌گیری نکن؛ طبق تصمیم انتشار، آن‌ها را در مرحلهٔ نهایی روی ماشین‌های آزمایش مجزا و پایگاه‌دادهٔ disposable ثابت کن.

## 7. ترتیب اجرا و نگهداری مسیر راه

1. نیازمندی و دامنهٔ V1 را از ماتریس canonical بخوان؛ scope را بدون تصمیم مالک خودسرانه حذف یا زیاد نکن.
2. Definition of Ready و Action Catalog را برای برش کامل کن؛ مالک، قرارداد و رفتار شکست/بازیابی را روشن کن.
3. UI همان قابلیت را کنار API/Server توسعه بده؛ صفحه و عملیات را تا حد امکان در یک برش قابل‌تحویل کامل کن.
4. آزمون‌های مرتبط و CI همان SHA را اجرا کن؛ شواهد و ریسک باقی‌مانده را ثبت کن.
5. Definition of Done را با شواهد واقعی کامل کن؛ «پیاده‌سازی شد»، «CI سبز»، «آزمون دستی»، «نصاب آماده» و «انتشار پذیرفته‌شده» را وضعیت‌های جدا نگه دار.
6. PRهای قدیمی را تنها پس از مقایسه با Integration جاری تعیین تکلیف کن. حذف شاخه‌ها کار نظافتی پس از تعیین تکلیف است؛ هیچ تغییر یکتای بررسی‌نشده‌ای را صرفاً برای کم‌کردن تعداد شاخه‌ها دور نریز.
7. وضعیت فازها، Issueها، PRها و SHAهای شواهد را پس از رویدادهای واقعی هماهنگ کن. به‌روزرسانی اسناد وضعیت نباید مرحلهٔ بسته را بی‌دلیل باز کند یا شواهد SHA قدیمی را به نسخهٔ جدید نسبت بدهد.

## 8. حد پذیرش

یک برش فقط وقتی Done است که معیار پذیرش Requirement ID برآورده، API/قانون در مالک درست، UI به عملیات واقعی وصل، خطا و مجوز و تکرار/رقابت مرتبط پوشش داده، آزمون‌های مربوط موفق و شواهد exact-SHA ثبت شده باشد. تکمیل دامنهٔ تجاری فقط زمانی اعلام می‌شود که تمام نیازمندی‌های اولویت‌دار نسخهٔ اول تکمیل یا با تصمیم صریح مالک به مرحلهٔ بعد منتقل شده باشند؛ انتشار نهایی علاوه بر آن به نصب/بازیابی و پذیرش فیزیکی برنامه‌ریزی‌شده نیاز دارد.
